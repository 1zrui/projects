# RPC 全熔断拖死主循环 → 漏掉 bBALL（12 分钟涨 6.5 倍）

## 现象
大哥发来 `0xed7e361f70ce5670f92eed4ce0dc520660677777`（bBALL）问特征。
排查发现：**链上扫描抓到了它的建池（20:10:24），但从未评估、从未推送。**

## 时间线
```
20:05:48  flap_new.jsonl 记录 bBALL 发币
20:10:24  chain_watch.log [新池] bBALL / BNB 池 0xcb9f...3737
20:08:58  [追赶] 本轮扫最近 600 块          ← 最后一次正常
20:20:36  [warn] eth_getLogs 失败: TimeoutError × 5 次
20:21:12  恢复评估
20:26:20  [P级-链上] bBALL 池龄16min 1分钟买58净$648 流$28,500   ← 重启后才补推
```
**期间 20:08~20:21 主循环被拖死 12 分钟**，bBALL 的成交数据全丢 →
评估时 `b1`（1分钟买单数）拿不到 → 不触发。同时快照 20:08 后停写、心跳 2 小时没打。

## 根因 ①：`rpc()` 的全熔断兜底写反了（主因）
```python
# 改前
live = [u for u in urls if time.time() - _node_bad.get(u, 0) > 60] or urls
                                                                  ↑ 全熔断时兜回全部
```
所有节点都在熔断期 → `live` 为空 → `or urls` 又拿回全部节点 → **每轮硬撞一遍、
每个白等 timeout(6s) 秒**。60 个池子的 Swap 查询叠加起来，单轮拖到几分钟。

**改法**：全熔断 → 本轮直接放弃，不等超时。
```python
live = [u for u in urls if time.time() - _node_bad.get(u, 0) > 60]
if not live:
    if time.time() - _all_dead_log.get("t", 0) > 60:
        _all_dead_log["t"] = time.time()
        log(f"[跳过] 所有节点都在熔断期，本轮跳过 {method}（不等超时，避免拖死主循环）")
    return None
```
（新增 `_all_dead_log = {"t": 0.0}` 做日志节流）

## 根因 ②：心跳的相位 bug（次要，但掩盖了故障）
```python
# 改前：循环周期若整除 300，相位固定 → 可能永远落不进那 4 秒窗口
if not seconds and int(time.time()) % 300 < 4:
# 改后：不依赖相位
if not seconds and time.time() - _last_beat > 300:
    _last_beat = time.time()
```
（新增局部变量 `_last_beat = 0.0`）

**教训：心跳本身写错时，故障期间反而"看起来正常"，排障时不要拿心跳当唯一判据。**

## 复用要点
1. **公共 RPC 全挂时，熔断兜底不能写 `or urls`** —— 那等于没有熔断。
2. **排查"某个币没被扫到"时，先看那段时间主循环有没有卡**（找 `[warn] timeout` 密集区）。
3. **心跳/快照的停写时间是判断"循环是否卡死"的第一手证据**（比日志内容更快）。
